Understanding Flow Builder

Required • 45 minutes

The Four Key Concepts

Flow Builder is MC Next's journey automation engine. Let's understand the building blocks:

1

Trigger Types

Every flow starts with a trigger that determines how members enter the journey:

  • Segment-triggered: Members enter when they join a segment (e.g., "New Members" segment)
  • Event-triggered: Members enter when a specific event occurs (e.g., "Trail Started" event from Data Cloud)
  • On-Demand: Manually trigger for a specific audience (e.g., flash sale announcement)
💡 Key Insight: For NTO's welcome journey, use segment-triggered. For trail promotions, use event-triggered to respond in real-time to member actions.
2

Interaction Elements

Interactions are the touchpoints where you communicate with members:

Available channels:

Email: Best for detailed content, product showcases, educational series
SMS: Urgent alerts, time-sensitive promotions, appointment reminders
WhatsApp: Two-way conversations, customer service escalations
Agent Handoff: Transfer to Service Cloud when journey needs human intervention

Each interaction element references content you've created in Content Builder.

3

Wait & Decision Splits

Wait Elements: Control timing between interactions

  • Wait for Duration: Fixed time (e.g., "Wait 2 days")
  • Wait Until Date: Specific date/time (e.g., "Wait until 10am Pacific")
  • Wait for Event: Wait until member performs action (e.g., "Wait for Purchase" up to 7 days)

Decision Splits: Branch based on conditions

  • Example: If LoyaltyMember.Tier = Gold → Send SMS + Email, else → Send Email only
  • Use for: Tier-based experiences, engagement-based paths, purchase behavior
💡 Best Practice: Use "Wait for Event" with a timeout. Example: "Wait for first purchase (max 7 days). If purchased → Send thank you. If timeout → Send incentive."
4

Agent Handoff

When automation isn't enough, hand off to Service Cloud for human intervention:

Use cases for NTO:

  • High-value tier escalation: Gold member has issue → Create case for VIP support team
  • Journey abandonment: Member doesn't engage after 3 emails → Trigger outreach call
  • Complex questions: Member replies to WhatsApp message → Route to agent

Agent Handoff creates a Service Cloud case with full journey context (which emails sent, clicks, opens).

Optimize Send Times with Einstein

Instead of blasting every eligible member at the same moment, let Einstein Send Time Optimization (STO) deliver each email at the time that member is most likely to engage. This is a great fit for the Spring Challenge Invitation — high-value members open on their own schedules, and STO learns each individual's pattern.

Enable Send Time Optimization (one-time admin step):

  1. In Setup, search for "Send Time" and click Einstein Send Time Optimization under Einstein for Marketing.
  2. Click Enable (the button changes to Deactivate once it's on).
  3. The status stays In Progress for up to 72 hours while Einstein trains on engagement history.
💡 Pro Tip: Enable STO early — because training can take up to 72 hours, turn it on well before you plan to send so it's ready when you activate the journey. STO also needs engagement history to learn from; in a brand-new org with little send history, expect the model to improve as data accumulates.

Apply STO to the journey's emails:

  1. Open the Spring Challenge Invitation email element (and then the Spring Challenge Reminder email).
  2. In the email's send settings, set the send timing option to Einstein Send Time Optimization instead of sending immediately.
  3. Save each email element.

Sending Beyond Flows: The Email Direct Send API

Concept • 15 minutes

So far every send in this module has been driven by a Flow — segment-triggered (Welcome, Spring Challenge Invitation) or event-triggered (Trail Promotion). There's a third pattern: sending programmatically from your own systems using the Email Direct Send API (GA August 2026).

🧠 What You Need to Know

What it is

A dedicated, purpose-built API for sending email at scale with a stable contract, predictable performance, and support for direct ingestion of HTML payloads.

Why it matters

Some messages are too time-sensitive to route through a scheduled journey — OTP and 2FA codes, order confirmations, password resets. Customers expect these in real time, and the API delivers that with predictable performance.

How it's different

No dependency on Flows or APEX classes for personalization — a CPaaS-grade message experience. It supports both promotional and transactional messaging and works out of the box in Marketing Cloud Next.

🎯 When to Use It (vs. a Flow)

Use a Flow when… Use the Direct Send API when…
The audience is a segment or a marketing event inside MC Next Your own app/backend needs to trigger a 1:1 message on its own event
Marketers build and own the journey (point-and-click) Developers build a programmatic or headless integration
Timing tolerates a scheduled/near-real-time journey The message is time-critical (OTP, 2FA, order/shipping confirmation)

⚙️ How It Works (the big picture)

Under the hood the API uses the High Scale Flow messaging service. Conceptually there are three moving parts:

  1. Authenticate — obtain an OAuth JWT bearer token with the sfap_api scope from an External Client App.
  2. Send definition — create a ListEmail object that references the (published) email content, sender identity, and tracking settings.
  3. Send — POST to the send endpoint with your sendDefinitionId, identifying recipients by individualId (single) or a recipients array (bulk). A preview endpoint renders without sending.
💡 NTO in practice: When a member redeems points and an order ships, NTO's commerce backend can call the Direct Send API to fire an instant shipping confirmation — no journey required. (The companion Transactional Order Triggers feature, also GA Aug '26, can fire these order/shipment/return messages automatically off the Data Cloud data model.)
💡 Pro Tip: This is a developer-facing capability. Marketers don't need to write code to benefit — but knowing the pattern exists helps you scope integrations with your engineering team. Full reference docs are linked in the hands-on section below.

Optional Hands-On: Send an Email via the Direct Send API

Optional • Developer • 30 minutes

⚠️ Optional & developer-focused: This section makes real API calls and is intended for developers or marketing technologists. Marketers can skip it — the concept above is enough for the rest of the training. You'll need permission to create an External Client App and access to a REST client (curl, Postman, etc.).

Prerequisites

  • High Scale Actions and Direct Email Send must be enabled for your tenant. If not, the API returns 403 - feature not enabled for tenant (contact your account executive).
  • Email content must be published in the marketing CMS before it can be sent.

Step 1 — Authenticate (Connect to the API)

  1. In Setup, create an External Client App and enable OAuth with the sfap_api scope.
  2. Relax or configure IP restrictions as appropriate for your integration.
  3. Request a token using the flow that fits your use case — Authorization Code (user-facing) or Client Credentials (server-to-server). The token must be a JWT; non-JWT tokens are not supported.
  4. Use the token as Authorization: Bearer <token> on every request.

📖 Reference: Connect to Direct Email Send API

Step 2 — Create a Send Definition (ListEmail)

Use the REST API to create a ListEmail object referencing your published content, sender identity, and tracking options, then deploy it. Note the resulting sendDefinitionId.

📖 Reference: Email — Manage Send Definitions (REST API)

Step 3 — Send (or Preview)

All endpoints use base URL https://api.salesforce.com/automation/actions360, require the sendDefinitionId query parameter, and the bearer Authorization header.

Optional Hands-On: Transactional Order Triggers

Optional • Admin + Developer • 40 minutes

🧠 What You Need to Know

The Direct Send API (above) lets your systems push a message. Transactional Order Triggers (GA August 2026) flips that around: it fires a Flow automatically when a real-time order event lands on the Data Cloud data model — order status change, shipment, or return — with no polling and no batch delay.

What it is

Real-time triggers that start a marketing Flow off order/shipment/return events delivered through a direct API integration on the Data Cloud data model.

Why it matters

Order and shipping notifications have some of the highest open rates in marketing. Customers expect them the moment the event happens — this delivers them automatically, at scale.

How it's different

Previously a Flow could only trigger on data changes in Data Cloud or the platform — not truly real time. Order Triggers fire on the transactional API event itself, integrated directly into the Flow.

💡 NTO in practice: A member redeems points for a jacket. The moment NTO's commerce system posts the shipment event, a Flow fires an "Your NTO Rewards order is on its way" email with the tracking number — and if the jacket is later returned, a separate "We've received your return" message goes out. No journey scheduling, no nightly batch.

Prerequisites

  • Data 360 (Data Cloud) provisioned in the org — order events land on its data model.
  • The Marketing Triggers Admin permission set assigned to whoever configures the trigger.
  • The order/shipment/return DMO fields mapped in Data Cloud (Step 1 below).
  • Published email content for each message you plan to send (shipment confirmation, return received, etc.).

Step 1 — Map the Required DMO Fields

The trigger reads its data from Data Cloud DMOs, so the order event fields must be mapped first. In Data Cloud, map the incoming order data to the order-event data model:

  • Order identity & recipient: the order/transaction identifier and the reference back to the Unified Individual (so the Flow knows which member to message).
  • Event type & status: the field that distinguishes order status vs. shipment vs. return.
  • Message payload fields: anything the email needs — e.g. tracking number, carrier, item name, order total, return reason.
⚠️ Verify against your org: exact DMO and field names for the order-event model depend on your data setup — resolve every mapping warning on the right of each DMO using your best judgement before continuing, the same way you did for Identity Resolution in Module 1.

Step 2 — Build the Event-Triggered Flow

  1. Create a new event-triggered Flow and choose the order event as the trigger source.
  2. Add a Decision / branch on the event type so each event routes to the right message:
    • Shipment → "Your order is on its way" email (include the tracking number attribute).
    • Return → "We've received your return" email.
    • Order status → optional order-confirmation or delay notice.
  3. Add the Send Email action on each branch, referencing the matching published content and mapping in the payload fields from Step 1.

Step 3 — Connect & Test

  1. Activate the Flow so it listens for live order events.
  2. Post a test order event through the API integration (or your commerce sandbox) — a shipment event for a known test member.
  3. Confirm the Flow fires in real time and the correct branch sends: check the Flow run and that the test member receives the shipment email with the right tracking number.
  4. Repeat with a return event to verify the second branch.
💡 Pro Tip: Pair this with the Direct Send API above — Order Triggers cover events flowing through your Data Cloud model automatically, while the Direct Send API is the escape hatch when a backend needs to push a one-off transactional message on its own terms. Together they cover both the automated and the ad-hoc transactional paths.

Deep Dive: Multi-Channel Orchestration & Error Handling

Optional • 30 minutes

Profile Selection for Multi-Brand Flows

If you're managing multiple brands (e.g., NTO Retail vs NTO Rewards), use profile selection:

  • Profile Selection element: Route members based on Brand preference
  • Example: If Brand = "NTO Retail" → Retail welcome journey, else → Rewards welcome journey
  • Benefit: One entry trigger, multiple brand-specific experiences

Error Handling & Flow Monitoring

Production flows need robust error handling:

Email Send Failures

What if an email bounces or member has no email address?

Solution: Add fallback path. If email fails → Send SMS (if available) or create Service Cloud case.

Event Data Missing

What if "Trail Name" field is missing in event payload?

Solution: Use default value. Example: {{Trail.Name | default: "an engagement trail"}}

Journey Monitoring

How do you know if a flow is broken?

Solution: Set up Journey Health alerts. Get notified if error rate exceeds 5%.

Multi-Channel Orchestration Best Practices

When mixing Email, SMS, and WhatsApp in one journey:

  • Check consent: Add decision split to verify member has opted in to SMS/WhatsApp before sending
  • Respect frequency: Don't send SMS and Email in same hour. Add 2-hour wait between channels.
  • Channel hierarchy: Use SMS for urgent/transactional, Email for promotional/educational
  • WhatsApp for two-way: Only use WhatsApp if you have agents available to respond

Advanced Wait Strategies

Beyond simple duration waits:

  • Einstein Send Time Optimization: Wait until optimal send time for each member (ML-powered)
  • Wait until attribute change: Wait until LoyaltyMember.Tier changes (max 90 days)
  • Business hours wait: Wait until 9am-5pm Pacific (don't send overnight)
  • Event-based wait: Wait for "Purchase" event (timeout 14 days)

Performance Monitoring in Production

Key metrics to track for each active flow:

  • Entry Rate: How many members entering per day? (Should match segment size or event volume)
  • Completion Rate: % of members who reach the end of journey
  • Drop-off Points: Where are members exiting early? (Indicates disengagement)
  • Error Rate: % of interactions that fail (email bounce, SMS error, etc.)
  • Engagement Rate: Opens, clicks, conversions per journey

Common Pitfalls & Solutions

⚠️

Pitfall: Members enter journey multiple times

Symptom: Sarah gets the welcome series twice

Solution: Set entry criteria: "Has not entered this journey before" or use "Entry limit: 1 time"

⚠️

Pitfall: Event-triggered flow fires too frequently

Symptom: Member starts 5 trails in 1 day → Gets 5 separate emails

Solution: Add "Frequency Cap: Max 1 entry per member per day"

⚠️

Pitfall: Personalization field missing

Symptom: Email shows "Hello, {{Individual.FirstName}}" instead of "Hello, Sarah"

Solution: Use default values: {{Individual.FirstName | default: "Valued Member"}}

When to Escalate

  • Complex business logic: If decision splits require 5+ conditions, consider splitting into multiple flows
  • Custom events: If needed event doesn't exist in Data Cloud, engage data team to create streaming event
  • Agent handoff setup: Requires Service Cloud configuration - engage Service Cloud admin
  • High-volume performance: If flow will send 1M+ messages/day, engage platform architect for capacity planning
